# 可自动运行、可评价、可回退的自进化方案

> 本文是完整路线图；`1.4.5-beta.1` 只实现其中的安全试运行基础。已实现的行为和使用命令见《技术方案报告》第 50 章。文中出现的成对评测、按错误率自动缩小范围、插件目标回归评价和核心功能补丁，仍属于后续阶段，不能把当前测试全绿当成效果已证明。

| 1.4.5-beta.1 已落地 | 尚待实现 |
| --- | --- |
| 明确偏好直接启用；推断偏好需用户原话支持、两个独立任务且只在相关任务试用；记录注入和明确反馈，支持停用/恢复 | 自动生成可检查的偏好验收标准、固定任务集的基线对照、统计性错误率 drop、按任务类型缩小适用范围 |
| 插件按文件哈希绑定隔离验证、测试和热加载；空插件无法通过验证；保存有效快照并支持回退 | 自动生成与原故障对应的回归用例、成对评测、线上退化自动熔断 |
| 普通任务和 `/loop` 都记录工具失败率；模型提出的护栏先待审核，重启后仅加载已启用规则 | 将趋势按环境/错误指纹分组、生成用户可审查的效果报告、自动修改核心功能 |

深度审查后的第一批断点已修复：普通任务会结算趋势，推断偏好经过用户原话检查并按任务相关性注入，模型提出的护栏先待审核。`/evolve verify` 和通用测试仍只能证明插件能加载且测试未报错，不能证明它修复了目标故障；没有基线对照和目标回归用例时，不应把趋势好转称为已证实的正向进化。

## 1. 目标与边界

目标是让 Flavor Code 随使用逐渐符合用户的工作方式，并持续降低可归因的工具故障。每次变化都必须能回答四个问题：为什么提出、在哪些任务生效、相比原版本带来什么收益、出现问题时如何撤回。

自进化对象分三层，自动化程度按风险递减：

| 层级 | 典型变化 | 自动落地策略 |
| --- | --- | --- |
| 偏好与记忆 | 回复格式、项目约定、用户纠正 | 用户明确表达的持久偏好可自动启用；推断出的偏好先试用，观测后晋级或撤回 |
| 提示词规则与插件 | 工具使用规则、工具包装或修复插件 | 自动提出、实现与验证；仅在版本绑定的门禁通过后进入可回退试运行 |
| 核心功能 | 修改内置工具、调度器或桌面端 | 自动生成隔离补丁、测试和评测报告；进入正常代码审查与发布流程，不能直接改动运行中的宿主 |

“自动”包括候选发现、测试、试用、观测、晋级和回退。当前用户指令始终覆盖历史偏好；权限、数据保护和安全边界不能被学习结果放宽。

## 2. 现状与必须先修的断点

- `src/memory/coordinator.ts` 已能在成功任务后提取候选，`src/memory/store.ts` 能持久化和召回。当前热度按召回次数计算，召回不等于有益；`feedback` 依任务文本召回，跨任务的行为纠正可能漏用。
- `src/evolve/service.ts` 能捕获重复工具失败并生成规则或插件建议，但服务启动时没有加载已存规则和建议到 `promptCache`。
- `/evolve reload` 可直接调用 `PluginHost.reload`；`verify`、`test` 和待加载插件内容没有绑定成一个强制门禁。
- 目前“自动验证”比较相邻两次运行中同一工具的失败次数。下一次没有调用该工具也会出现负 delta，进而误把建议标为有效。累计失败数 `signalDelta` 也不是可下降的质量指标。
- `src/eval/runner.ts` 主要检查命令结果和 token 预算，尚无“是否更符合用户偏好”的评测维度。
- `src/sleep/organizer.ts` 的日报是离线报告，默认关闭，也没有把发现转入受控候选流程。

先修上述正确性问题，再开放自动试用。已有历史 `verified.json` 只能作为旧状态展示，不能直接作为新版门禁证据。

## 3. 一条统一的变化生命周期

```text
观察信号 → 生成候选 → 去重/冲突检查 → 离线验证 → 试用 → 归因观测
                                  ↘ 拒绝/搁置      ↘ 晋级或回退
```

每条候选使用同一状态机：

```text
proposed → eligible → evaluating → canary → active
     ↘ rejected        ↘ rejected     ↘ suspended → dropped
                                  ↘ suspended      ↘ revised → canary
```

状态记录至少包含：`id`、`kind`、`scope`、`source`、`evidenceRefs`、`targetId`、`contentHash`、`successCriterion`、`status`、`createdAt`、`activatedAt`、`evaluationVersion`、`rollbackRef`。`successCriterion` 定义该候选预期改变的可观察行为；无法写出可检查标准的推断候选可以保留为建议，但不能自动晋级。状态转移写入追加式日志，当前状态可由日志重建。候选内容使用受控文件或现有记忆正文存储，日志只保存必要摘要与引用，不复制原始会话、工具参数或密钥。

`scope` 至少区分 `user_global`、`workspace` 和 `task_pattern`。同一主题的新偏好应更新或取代旧记录，而不是不断追加相互冲突的指令。用户显式纠正的权威高于行为推断；当前任务的相反要求只抑制本次偏好，不自动删除长期偏好。

### 3.1 候选发现

从现有 `UserPromptSubmit`、`Stop`、`PostToolUse`、`PostToolUseFailure`、`PermissionRequest`、`LoopEnd` 采集候选信号，并补充结构化的用户反馈事件。

- **明确表达**：“以后都用中文解释”“这个项目不要自动提交”等，由用户原话生成偏好候选；通过敏感信息和冲突检查后自动启用，并提供撤销入口。
- **重复纠正**：相同纠正在不同任务中出现至少两次，才提出推断候选。模型输出只是候选，不能凭一次沉默、一次工具使用或模型自评建立持久规则。
- **工具故障**：沿用现有去重机制，但排除用户取消、预期的探测失败和不同工具/环境的混合归因。记录相关工具调用数作为分母。
- **反向信号**：用户否定、重新要求、撤销编辑、回滚、测试失败和权限拒绝。负面信号不能被多次“召回”抵消。

### 3.2 偏好试用

明确、持久且无冲突的用户偏好直接成为 `active`；模型推断的偏好进入 `canary`，仅在命中任务范围时注入。试用规则在动态上下文段注入，避免频繁变化破坏稳定提示词缓存。用户可以在 `/memory` 或桌面端看到“来源、适用范围、试用状态、最近效果”，可编辑、停用或永久确认。

把“记忆被检索”和“记忆发挥作用”分开记录：`retrieved`、`injected` 是暴露事件；任务结果和后续用户反馈才是效果证据。不能再用召回次数给记忆自动加权。稳定行为纠正应按适用范围注入，不依赖任务文字的词法相似度。

### 3.3 插件与功能试用

插件候选自动在隔离目录实现，计算整个插件目录的内容哈希，然后依次通过：

1. 清单、权限变化和危险能力检查；新增网络、宿主文件系统或更高权限时停止自动激活。
2. 影子 `PluginHost` 加载和贡献声明校验。
3. 与失败信号对应的回归用例、相关测试、完整测试套件。
4. 在冻结任务与工作区快照上比较原版和候选版；确认目标故障得到修复，且关键任务没有退化。

`verify` 与 `test` 结果必须记录相同的内容哈希、命令、退出码、时间和环境指纹。`reload` 只接受有合格记录的当前哈希。试运行按任务或项目开关启用，保留上一个有效快照；触发回退条件时自动停用并恢复。核心功能变化沿用相同评测，但产物是分支/补丁和报告，不直接热更新宿主。

## 4. 评价：先看硬门槛，再看可归因收益

### 4.1 硬门槛

任何候选只要违反用户当前指令、权限边界、敏感信息规则或关键回归测试，就判为失败。用户明确否定某条试用偏好时立即停用；插件发生新的严重故障时立即回退。硬门槛不能被其他正向指标抵消。

### 4.2 按候选记录暴露与结果

每次适用任务写入 `exposure`：`taskId`、任务类别、候选 ID 与哈希、是否实际注入/启用、相关工具调用数、测试与任务结果、用户后续纠正、撤销/回滚、耗时和 token。只记录必要的统计与会话引用。

| 目标 | 主指标 | 辅助指标 |
| --- | --- | --- |
| 偏好 | 适用任务中的重复纠正率、明确采纳/否定 | 为达成同一要求追加的提示次数、用户主动撤销次数 |
| 工具修复 | 同类环境中每次相关工具调用的失败率、原故障复现率 | 任务通过率、超时率、调用成本 |
| 功能变化 | 固定验收用例通过率、用户接受的成果比例 | 完成时间、token、回滚率 |

比较采用两层证据：先在同一冻结任务/工作区上做原版与候选版的成对评测；上线后再观察命中候选的真实任务，并按任务类别和环境分组。成对评测要检查 `successCriterion`，同时覆盖不相关任务与冲突指令，防止规则过度泛化；模型输出不稳定时重复运行并报告波动。没有足够的可比任务时保持 `canary`，不因“零失败”自动晋级。真实任务主要用于发现伤害；没有用户纠正只是一条弱证据。模型评委可辅助解释差异，但不能代替可观察断言、测试结果和用户反馈。

首版不设单一加权总分。初始门槛可设为：至少两条独立的推断来源；偏好成对评测覆盖至少五个任务，其中包含相关、不相关和冲突用例；试用至少命中十个真实任务；插件必须让目标回归用例从失败变为通过，且全部关键测试通过。偏好晋级还要求可观察的遵循率优于基线、关键指标不退化且没有明确负面反馈。样本不足或效果不确定时保持试用状态。具体数量是起步配置，需用实际样本和成本校准；仪表盘展示样本数、基线和不确定性，避免把一次偶然成功称为进步。

### 4.3 偏好自动收缩与 drop

偏好出现较多错误时可以自动 drop，但“错误”必须关联到这条偏好实际注入的任务。统计用户明确纠正或否定、可检查的偏好违反、因该偏好导致的任务失败；按相关任务数计算错误率，不用绝对次数或普通工具失败代替。对照评测需关闭该偏好再运行同类任务：两边都失败，不能把责任归给偏好。

处理顺序是 **暂停注入 → 判断范围 → 缩小/改写或 drop**：

- 用户明确说“别再按这条做”，立即 `suspended`；严重安全或权限回归也立即暂停。
- 错误集中在某类任务时，将 `scope` 缩小并重新进入 `canary`，例如只在“写设计文档”时生效。
- 多个独立任务中都出现可归因负面结果，且成对评测没有证明收益时，进入 `dropped`。起步门槛可设为至少十次适用暴露、至少三个独立任务的负面证据，并要求错误率高于未启用偏好的基线；具体门槛可配置并用数据校准。
- 用户明确确认的偏好遇到统计性退化时可自动暂停，但不因模型自己的判断永久删除；展示原因，由用户决定是否改写或放弃。当前用户的明确撤销可直接 drop。

`dropped` 表示不再检索或注入，不是物理删除。保留候选版本、来源、评价和恢复入口，防止同一内容被随后再次自动提出；用户要求彻底忘记时才清除对应数据。没有命中任务、没有反馈或样本不足都不构成 drop 证据。

### 4.4 自动回退

回退由具体候选 ID 与哈希触发：明确用户否定、关键测试失败、目标失败率显著恶化、权限边界变化或数据校验失败。回退只撤销该候选；保留原因和证据，不清空历史。被回退候选不能在同一内容哈希上自动重试。

## 5. 实施顺序与验收

### 阶段 A：修复现有闭环的正确性

- `createEvolveService` 增加显式 `initialize(): Promise<void>`，生产运行时在创建上下文前等待规则和建议加载。
- 移除按相邻运行绝对失败次数自动写 `verified.json` 的逻辑，改为记录“待评估”；修正趋势为按相关调用次数计算，并保留工具/错误指纹维度。
- 为插件验证、测试和加载添加内容哈希门禁；只把通过全部门禁的快照标为 `lastKnownGood`。
- 扩大错误信息脱敏，避免未加引号的路径或令牌进入失败信号。

验收：重启后已有规则立即生效；未验证或验证后改动的插件无法热载；零相关调用不产生“有效”判定；失败的候选能恢复上一有效版本。

### 阶段 B：项目级偏好自动试用

- 新增 `src/evolution/`：候选日志、暴露记录、状态机、冲突检查与评价器。自动候选单独存储并按状态注入，复用 `MemoryStore` 的规范化和安全校验；已有手工记忆照常工作，不迁移索引。这样试用或回退候选不会被现有 `userContext()` 无条件注入。
- 从明确用户纠正生成带来源的候选；推断候选只进入试用。补充 `/evolve candidates|history|rollback <id>` 和桌面端的来源/状态展示。
- 在任务上下文记录候选暴露，并把后续纠正关联到原任务和候选。

验收：明确偏好在新任务中生效；一次偶然行为不会成为偏好；相反纠正会取代旧偏好；用户撤销后下一任务不再注入；跨任务可归因错误触发暂停或 drop，局部错误只缩小适用范围；每条偏好能查看命中任务、正反反馈和恢复入口。

### 阶段 C：插件自动修复与成对评测

- 扩展 `src/eval/schema.ts` 与 `runner.ts`，支持任务类别、基线/候选版本、目标断言和结果差异。
- 为重复故障自动生成受限修复候选与回归用例，在隔离工作区完成验证；通过后按项目试运行并监控。
- 核心功能候选输出补丁和评测报告，接入现有审查流程。

验收：同一故障可从捕获走到可回退试运行；目标故障不再复现，关键评测不退化；负面反馈或回归会自动停用该版本；评价报告能列出基线、候选、样本和证据。

### 阶段 D：跨项目习惯与长期维护

- 在项目级方案验证有效后，引入用户全局偏好存储；只把明确跨项目适用的偏好提升到全局。手工 `GLOBAL.md` 保持更高优先级。
- 让睡眠整理只提出候选，不直接改写偏好；定期合并重复项、识别过期项目规则，并在删除前保留可恢复历史。

## 6. 最小端到端场景

用户两次指出“解释修改时先说影响，再列测试结果”。系统将这两次纠正关联成一个项目级偏好候选，验收标准是输出确实按该顺序呈现。检查与现有规则无冲突后，先用冻结任务比较原版和候选版，再自动试用。试用只在相关的交付说明任务中注入并记录暴露；若用户再次纠正，候选调整或停用；若成对评测和足量真实任务都显示遵循率改善、关键指标未退化且没有负面反馈，候选晋级为稳定偏好。用户随时能看到其来源、效果和撤销入口。

这条链路跑通并通过验收后，再开放插件自动修复；否则“自进化”只能增加规则数量，无法证明体验在变好。
